# 希维塔大陆横向扩展审计

更新时间：2026-08-08。本页把“单个 Paper 能承载多少人”和“整个网络累计在线多少人”分开。任何配置值、空服 TPS 或平均值都不能替代同版本、同世界、同插件、同数据库的分布式压测证据。

## 当前事实

| 边界 | 当前证据 | 结论 |
|---|---|---|
| 单实例 | `max-players=100`；性能基线要求先证明 50 人，再证明 70/100 人 | 100 是拒绝连接的上限，不是已证明容量 |
| 网络入口 | 没有 Velocity 配置、代理服务、modern forwarding 密钥或后端防火墙模板 | 当前只有一个可直接连接的 Paper，不是服务器网络 |
| 游戏数据库 | LAN 的 `server/.env` 明确不设置 `RPG_DATABASE_*`，因此使用本地 H2 | 当前数据不能被第二个 Paper 共享；改 URL 也不会自动搬运 H2 数据 |
| 连接预算 | 每个 Paper 默认 6 个 Hikari 连接，网站最多 4 个；Compose 的 PostgreSQL 默认 `max_connections=40` | 直接连接模型为 `6 × Paper节点数 + 4 + 运维余量`；保留 4 条运维连接时最多只能容纳 5 个默认 Paper 池 |
| 可观测性 | 每个 Paper 原子写本地 `plugins/RpgPerformance/status.json`；网站只读一个 runtime 目录 | 能观察单节点，不能汇总全网在线、节点容量、路由或分片健康 |
| 备份 | 文档要求每日全量和 15 分钟 WAL，但仓库没有 `pg_dump`、WAL 归档、恢复脚本或演练产物 | 这是运维目标，不是已交付的灾备能力 |

若单 Paper 最终实测稳定容量为 50–70 人，10,000 同时在线的量级意味着约 143–200 个等价游戏后端，而不是把一个 JVM 的堆继续放大。大厅、持久生存世界、资源世界和副本的单位成本不同，最终节点数只能由各角色的独立压测相加得出。

## 状态边界审计

### 已具备 PostgreSQL 并发边界

角色档案、等级/体力、金币/功勋/星辉账本、学习技能、职业分支、章节、市场托管与邮箱、商业额度、委托证据和社群状态已经由 `RpgCore` 事务持久化。关键写路径普遍使用行锁、条件状态转换或幂等键；市场过期扫描也不会因多个节点重复返还。

PostgreSQL 启动迁移已有互斥：所有 Paper 在执行加法式 `CREATE/ALTER/INDEX` 前取得同一把事务级 advisory lock，并在 30 秒后失败关闭。它避免滚动发布时 DDL 竞态，但不替代正式的版本化迁移工具、PostgreSQL 集成测试或玩家跨服会话协议。

副本体力预留现在有第一条真正的跨节点 fencing 边界：每个 Paper 用稳定 `RPG_NODE_ID` 和随机进程 token 在 `rpg_node_leases` 持有 PostgreSQL 租约；预留记录精确 owner。启动和周期恢复只退款没有有效 owner token 的记录，不再由“任意第二节点启动”退款第一节点的活动预留。过期 token 不能续租，也不能 commit/refund；数据库短暂故障会在租约到期前重试，确认失租后 `RpgCore` 失败关闭。跨节点、替换进程、过期 token 和重复恢复已有 H2 PostgreSQL-mode 单元测试；真正两节点 PostgreSQL `kill -9` 演练仍是 S1 门槛，不能用单测冒充生产证明。

### 仍绑定单节点或单世界的数据

| 类型 | 当前落点 | 横向扩展前必须做的事 |
|---|---|---|
| 原版背包、末影箱、位置、生命和签名装备 ItemStack | 每个后端自己的玩家 `.dat` 与物品 PDC | 建立有 fencing token 的玩家会话租约与原子交接；禁止两个节点同时加载同一玩家存档，也不能把同一 world/playerdata 目录并发挂载给多个 Paper |
| 新手旅程、外观选择/解锁、视觉偏好、副本保底/返回点、战斗截止时间、硫灵额度等 | 玩家 PDC | 按“安全/玩法/仅视觉”分类迁入共享档案或纳入一次性玩家交接 payload；本轮只解决体力预留，不等于副本 session 已可切服 |
| 技能冷却与法力、战斗内存、队伍/副本 session、排队和 AI 会话 | JVM 内存 | 明确切服时重置的非关键状态；其余状态写带版本的 session authority，并用节点租约防止旧节点继续结算 |
| AuthMe、LuckPerms | 当前单服 SQLite | 迁移到网络级身份方案与 PostgreSQL；代理必须成为唯一公网入口，后端端口用防火墙隔离 |
| Citizens/BetonQuest 状态、世界与区块 PDC | 本地插件/世界文件 | 静态大厅和持久世界采用单写者归属；动态副本从只读模板创建，不把同一世界目录交给多个进程 |
| 性能、经济与章节快照 | 单节点本地 JSON | 快照必须带 `node_id`、schema、采样时间和修订号，推送到集中指标系统；网站不能通过共享目录猜测全网状态 |

原先的明确阻断点 `JdbcDungeonEntryService.recoverAll()` 已按 owner node/process token 修复。现在的主要阻断点上移到完整玩家会话：背包、位置、PDC、战斗和副本世界 session 仍没有统一 fencing token，因此现阶段仍不能让同一 UUID 在两个 Paper 上同时加载，更不能把同一世界目录交给两个进程。

## 目标拓扑

```text
玩家
  -> L4/TCP 入口与限速
     -> 多个 Velocity 入口（无唯一玩法状态）
        -> 大厅池
        -> 持久生存 Realm/线路（每个世界单写者）
        -> 资源世界池（按周期轮换）
        -> 副本工作池（模板化、可回收）

所有后端
  -> 玩家会话/路由权威
  -> PostgreSQL（玩法唯一事实源）
  -> Redis（只做通知、短租约提示和缓存失效，不做余额或物品唯一真相）
  -> 集中指标、日志和追踪
```

“万人”应由多个明确 Realm/线路和副本工作池相加。一个连续可破坏的生存世界不能简单复制后同时接受写入；需要按 Realm 选择、区域所有权或其他玩家可理解的边界分片。首选 Realm/线路是因为它不改变现有 Paper 插件线程模型，也比在同一世界上做跨进程区块所有权更容易证明不会复制物品。

## 分阶段交付门槛

### S0：把单服基线证明完整

1. 在预发布机把 H2 **显式导出、校验行数和导入 PostgreSQL**；只切换 JDBC URL 不算迁移。
2. 完成 PostgreSQL 30/50/70/100 阶梯压测、2 秒延迟、30 秒断连和模糊提交测试。
3. 交付可执行的全量备份、WAL 归档、时间点恢复和异机恢复演练。
4. 生产 preflight 现在同时验证游戏端 `RPG_DATABASE_URL`、凭据和非 `standalone` 的 `RPG_NODE_ID`；生产 systemd 还设置 `RPG_REQUIRE_POSTGRESQL=true`，即使跳过 preflight 也不能静默回退 H2。

H2 数据复制与逐表校验工具已经交付在 `server/bin/migrate-rpg-h2-to-postgresql.sh`，包含双重停服门禁、只读源、schema/唯一键兼容检查、空目标或显式覆盖策略、单事务批量复制、提交前后行数/主键/全行/关键金额校验、dry-run 和幂等复验；操作手册见 `docs/DATABASE_MIGRATION.md`。本仓库尚未用生产数据副本完成一次真实 PostgreSQL 恢复与迁移演练，因此 S0 仍未宣告通过。

### S1：两节点金丝雀

1. 部署一个 Velocity 和两个仅内网可达的 Paper，启用 modern forwarding 与独立密钥。
2. 为每个进程配置稳定唯一的 `node_id`。数据库节点租约及副本体力 fencing 已完成；仍需把同一 token 扩展到玩家单活、切服和入站/出站幂等交接，不能把局部完成写成整条完成。
3. 首先拆无共享世界写入的大厅或副本；不先复制主生存世界。
4. 将 AuthMe/LuckPerms、玩家 PDC 状态、背包/末影箱和技能冷却策略逐项迁移并做 `kill -9` 切服测试。
5. 在真实 PostgreSQL 两节点环境验证已修复的 `recoverAll()`：活动 owner 保持不变，`kill -9` 后到期 owner 只退款一次，旧进程恢复网络也不能结算。

### S2：网络化运营

1. 多 Velocity 入口放在 L4 负载均衡后；连接限速、封禁和注册风控在入口层统一执行。
2. 引入 PgBouncer 或等价连接治理，按数据库压测确定池大小；禁止把数百个 Paper 的 6 连接直接相加后交给 PostgreSQL。
3. 指标按 `proxy/node/role/realm/build` 聚合，记录全网在线、路由失败、切服延迟、MSPT P95/P99、JDBC 等待、队列、GC、世界/实体量和经济结算失败。
4. 使用 transactional outbox/inbox 传递跨服通知；余额、装备和市场仍以 PostgreSQL 事务为准，Redis 丢失不得改变结算结果。

### S3：向万人容量扩展

1. 按大厅、Realm、资源世界和副本角色分别做容量曲线，再依据峰值和 N+1 故障余量计算节点数。
2. 世界节点按单写者调度，副本工作节点按模板和 session 租约弹性扩容；升级采用分批流量迁移，不让不同 schema 节点同时写不兼容 payload。
3. 进行代理故障、Paper 硬崩、数据库主备切换、Redis 清空、网络分区和回滚演练。
4. 只有 10,000 个真实协议连接的混合行为压测、经济幂等重放和至少一次节点故障仍满足门槛，才能宣称“万人网络容量”。

## 必须保持的验收不变量

- 同一 UUID 任意时刻只有一个持有效 fencing token 的游戏节点。
- 切服每个阶段重复、乱序或超时都不能复制/丢失背包、装备、货币、体力和邮箱物品。
- 新节点启动不能退款其他节点仍有效的副本预留，也不能重复执行一次性奖励。
- 所有数据库池之和低于治理后的连接预算，并始终保留监控、迁移和故障处理连接。
- 单节点状态不得冒充全网状态；任何陈旧或缺失节点样本都必须显示为未知/降级，而不是健康。
- PostgreSQL、世界和身份数据都必须从独立备份恢复成功，文档中的计划不能替代恢复产物。

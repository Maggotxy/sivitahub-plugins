# 希维塔大陆任务与剧情架构

## 结论

希维塔大陆需要任务层，但不应转型为强制阅读长对白的传统剧情服。服务器的辨识度来自“原版行为 → 自制装备 → 动态战斗 → 副本与经济”的闭环；剧情的职责是解释、引导和改变这个闭环，而不是在闭环外另建一条一次性消耗内容。

采用“系统驱动的轻主线”：

- 序章和主线只负责解锁、教学、世界变化与核心系统之间的因果关系。
- 职业支线表现导师、技能代价、晋升选择和隐藏职业试炼。
- 原版世界事件使用调查、追踪、守卫、撤离和生态委托，而非重复击杀计数。
- 大型章节按赛季少量发布，用来解释新副本、职业分支、血月阶段和主城变化；玩家仍可跳过对白自由生存。
- 每个任务节点必须至少推动一个真实系统状态。纯跑腿、无变化的长距离寻路和重复对白不得进入正式内容。

## 哪些内容需要任务，哪些不需要

| 内容 | 是否任务化 | 原因与实现 |
|---|---|---|
| 首次职业、锻造、原版共鸣和副本 | 是，一次性轻主线 | 玩家需要理解系统因果；节点只解锁入口、校验真实行为或给一次性补偿，不替代玩法本身 |
| 资源委托、市场、商店 | 否，保持服务循环 | 这是经济供需与金币回收，不应伪装成每天重复读对白的“日常任务” |
| 血月、连猎、稀有怪 | 事件化支线 | 调查、守卫、撤离和贡献结算能改变当晚玩法；普通刷怪不额外套任务计数 |
| 普通/隐藏副本 | 少量章节任务 | 任务负责给出动机、线索与特殊入口，体力、门票、Boss、掉落仍由副本服务判定 |
| 职业晋升与隐藏职业 | 是，条件型支线 | 五维、等级、职业方向和材料必须由职业服务复核；剧情只表达选择与代价 |
| 长期终局 | 不做无限主线 | 依靠轮换词缀、竞速、收藏、构筑、锻造者名望与赛季事件，避免一次性剧情耗尽后失去目标 |

这让任务成为“理解与改变玩法的接口”，而不是另一套经验条。新章节若删掉对白后对世界状态毫无影响，就不应立项。

## 任务层级，而不是一张无限清单

| 层级 | 周期 | 是否独立计数 | 在本服的用途 | 当前状态 |
|---|---:|---|---|---|
| 核心旅程 | 每账号一次 | 只记录完成位，不生成新经验条 | 教会职业、五维、原版探索、动态野怪、锻造、槽位成长和副本 | 8 个真实状态目标已接入菜单与剧情 NPC |
| 轻主线 | 每章节少量 | BetonQuest 只保存对白/演出标签 | 解释系统因果、表现选择、触发受控演出 | 序章“共鸣巡路”已实现 |
| 资源委托 | 日常轮换 | 使用经济服务额度 | 把原版材料带入供需和金币回收 | 已由 `rpg-economy` 实现，不包装成长对白 |
| 世界事件任务 | 事件期间 | 复用事件贡献与额度 | 血月调查、守卫、撤离、稀有怪追踪 | 血月/连猎与章节服务已有；剧情化贡献内容待制作 |
| 晋升/隐藏支线 | 每次晋升或一次性 | 复用职业、技能、装备条件 | 表达职业代价和特殊路线 | 两条隐藏路线已有权威资格、名额和激活事务；后续只补不改变规则的剧情试炼 |
| 赛季章节 | 每赛季少量 | 复用 `RpgCore ChapterService` 权威状态 | 开启新副本、词缀、主城变化和服务器首杀 | 四章单向闸门、审计历史、职业晋升和官网快照已实现；后续只补内容 |

章节不会在第几周到点自动开启。管理员只能执行 `/rpgadmin chapter advance <下一章ID> CONFIRM <原因>` 推进紧邻下一章；数据库修订号、操作人、原因和时间全部保留。BetonQuest 可以根据章节选择对白，但不能自己改章节或绕过职业、副本和经济服务。

核心旅程允许玩家乱序游玩：例如先探索再分配属性，探索记录不会丢失；界面始终显示按推荐顺序找到的第一个未完成目标。任务完成来自真实事件、角色档案和签名装备，不能通过重复对话推进。每步奖励使用固定幂等键进入现有活动经济额度，因此断线可重试但不能重复铸币。

当前单 Paper 服把核心旅程完成位保存在玩家 PDC，和原版玩家数据一起落盘；这对现阶段部署可靠且读取无需 JDBC。未来拆成多个 Paper 分片前，完成位必须迁入 PostgreSQL 或随权威玩家会话交接，BetonQuest 标签也必须采用共享存储，不能把单服 PDC 直接宣称为跨服方案。

## 选型边界

| 层 | 方案 | 负责 | 明确不负责 |
|---|---|---|---|
| 固定服务 NPC | Paper 26.2 Mannequin + Dialog | 菜单、锻造、市场、副本等高频柜台 | 长距离移动、护送 |
| 动态演员 | Citizens2 | 私有演员、导航、跟随、护送、巡逻、剧情走位 | 核心货币和角色数据 |
| 剧情编排 | BetonQuest 3.1 | 分支对白、条件、标签、目标、章节内容包 | 任意控制台命令、直接发核心奖励 |
| 白名单桥 | 自研 RpgStory | 职业条件、并发保护、负载降级、幂等奖励 | 通用脚本执行器 |
| 唯一事实源 | RpgCore 服务 | 角色、金币账本、装备和其他核心状态 | NPC 表演状态 |

Citizens 官方 API 提供 NPCRegistry、Navigator、Trait 和导航事件；BetonQuest 3.1 官方集成支持 Citizens NPC、移动动作、会话、条件与目标：

- https://wiki.citizensnpcs.co/API
- https://betonquest.org/3.1/Documentation/Reference/Integrations-List/NPCs/Citizens
- https://betonquest.org/3.1/Documentation/Advanced/Conversations/

`RpgStory` 在插件加载阶段注册 BetonQuest 自定义动作与条件，早于剧情包解析；运行阶段才接入角色、旅程、菜单、性能和账本服务。这样全新服务器第一次冷启动就能加载内容包，不需要先报错再手动重载。BetonQuest 的 `first` 节点会按条件选择第一个可用分支，正适合让同一个 NPC 根据真实下一步显示不同对白；核心击杀、装备与奖励则不使用 BetonQuest 通用 objectives 重复监听。BetonQuest 会异步筛选对白条件，因此条件只读由主线程发布的不可变旅程快照；打开菜单、生成演员和结算奖励的自定义 action 则显式声明必须回到主线程。

## 已实现纵切：序章·共鸣巡路

主城 `Citizens ID 9101` 的“巡路人 · 栖枝”承载中英文 BetonQuest 分支对白。玩家选择基础职业后可以开始巡路；每位玩家获得一个只对自己可见的内存 Citizens 演员，路线依次经过引导区、共鸣树、锻造区、副本区和荒野门。

护送具备以下生产边界：

- 最多 12 个并发私有演员；服务器负载严重时拒绝新会话并暂停现有导航。
- 10 tick 合并检查一次；没有逐 tick 插件扫描。
- 玩家落后 14 格时演员暂停等待，超过 30 格并持续 12 秒才重置。
- 寻路失败最多重试 3 次，总时限 8 分钟；失败不写完成状态、不扣物品。
- 普通负载下仅向任务本人低频发送 2 个粒子；压力状态关闭粒子。
- 完成奖励为 300 金币，可用于前期补给或后续普通锻造；职业礼包的第一次锻造本身为 0 金币、100% 成功。
- 奖励使用 `story:<任务>:<玩家 UUID>` 账本幂等键。即使重复交互或数据库响应丢失，也不会重复铸币；`/story claim` 可恢复待确认奖励。

巡路结束后，栖枝会读取统一核心旅程的真实完成位，针对下一步解释它和整体循环的关系，并通过受信任的 `GuideMenuService` 直接打开对应旅程菜单；YAML 不执行玩家命令。玩家入口：`/story status|next|start|claim|cancel|help`。`/language zh_cn|en_us` 会同步 BetonQuest 的 `zh-CN/en-US` 会话语言。

核心旅程当前顺序为：认识主城 → 选择职业 → 分配五维并学习首技 → 完成保底首铸 → 完成原版进度 → 击杀动态野怪 → 揭示首个属性槽 → 击败副本 Boss。这是一条推荐路线，不是八道门：后完成的服务状态会独立记录，剧情只指出最前面的缺口。

### 玩家看到的状态不是内部诊断

`/story status` 现在打开玩家任务面板，先明确区分“约三分钟的可选主城巡路”和“由真实玩法自动推进的八项新手旅程”。面板只回答四件事：现在做什么、去哪里、为什么、下一步解锁什么，并给出一个主操作按钮。Citizens 演员并发数、容量上限、内部枚举和 BetonQuest 标签仅保留在 `/storyadmin status` 与日志中，绝不再出现在玩家文案。

断线或重启遗留 active 标签、但私人回声已经消失时，状态会明确显示“恢复主城巡路”；重新生成从安全起点开始，奖励仍由同一个幂等流水结算。巡路完成后，面板自动切换到八项旅程中第一个真实缺口，而不是继续要求玩家重复剧情。

旅者罗盘不是一张静态说明书。每次旅程状态发布、真实目标完成、玩家重生或重新上线时，原物品会原位刷新名称与 Lore：首行显示当前目标，随后显示地点、意义和右键入口；八项完成后切换为自由旅程入口。右键罗盘直接打开当前目标页，按 G 才是完整总菜单，避免常驻 BossBar 或侧栏产生屏幕噪音。

任务与委托中心已有“系统旅程”入口，闻见者的本地知识库也能解释巡路规则。剧情中断后不会写完成状态；重启遗留的进行中标签可以通过 NPC 对话或 `/story start` 重新生成私有演员。

## 后续内容准入

以下场景适合继续使用 Citizens 动态演员：

- 隐藏副本侦察：玩家保护受伤的侦察员抵达随机入口，入口本身仍由副本服务校验体力和门票。
- 血月撤离：公共事件中分批护送村民，奖励由活动额度与贡献账本结算。
- 隐藏职业试炼：演员根据职业、五维和前置技能显示不同路线；最终激活必须调用隐藏路线服务。当前血契和符箓的资格还会复核已学技能、对应隐藏副本回执与全服名额，演员本身不保存或发放资格。
- 大型章节：仅在剧情移动确实表达世界变化时使用 NPC 走位，普通交谈仍用固定 NPC。

不适合使用动态演员的内容包括商店、锻造、市场、日常委托领取和 AI 问答。这些交互频率高、无需路径寻找，继续使用原生固定 NPC 更稳定。

## 调研依据

- BetonQuest 3.1 官方文档把 conversations 定义为问答序列，`first` 会选择第一个满足条件的 NPC 节点，且原生支持 `menu`/`tellraw` 回退和逐字段多语言。这正是本服“同一 NPC、按真实状态给下一步”的内容层需求：https://betonquest.org/3.1/Documentation/Advanced/Conversations
- BetonQuest objectives 可以监听击杀、方块等目标，但本服这些状态已经由动态怪、装备、副本和经济插件权威处理。再建一份 objective 会产生双计数和绕过规则的风险，所以只把对白标签交给 BetonQuest：https://betonquest.org/3.1/Documentation/Basics/Scripting-Elements
- Citizens 官方 API 建议导航目标只设置一次、使用 local parameters，并可监听导航事件；现有护送按路点设置目标，限制演员数量并在压力状态暂停，不把固定商店 NPC 迁入寻路层：https://wiki.citizensnpcs.co/API
- Citizens 与 BetonQuest 的 NPC 集成只负责绑定对话和演员表现，核心状态仍经自研白名单桥复核：https://betonquest.org/3.1/Documentation/Reference/Integrations-List/NPCs/Citizens
